# Bolthole protocol, version 1

This document is the whole contract. Any language that can open a WebSocket,
compute SHA-256 / HKDF / HMAC, X25519 and AES-256-GCM can implement an agent,
a client or a relay from it. `spec/test-vectors.json` pins every derived value
and a complete handshake byte for byte; the Go and JS implementations are both
checked against it.

```
service (agent) ──WSS /v1/agent──▶  relay  ◀──HTTPS/WSS /c/<token>/…── client
        └──────────── end-to-end encrypted session (relay sees ciphertext) ───┘
```

Words used below:

| Term | Meaning |
| --- | --- |
| **agent** | The process that offers a service. It dials **out** to the relay, so it needs no public address, port forwarding or VPN. |
| **client** | Whatever wants to reach the agent: a phone, a browser, a CLI, another server. |
| **relay** | A dumb, stateless router between them. It stores nothing on disk and, in E2E mode, cannot read or forge traffic. |
| **connect code** | 32 random bytes the agent generates. It is the only secret; whoever holds it can reach the agent. |
| **session** | A multiplexed connection carrying many **streams** (§3). |

The layering, from the bottom:

1. **Transport**: WebSocket messages (§2).
2. **Mux**: framed, flow-controlled, bidirectional byte streams over any
   message transport (§3).
3. **Stream kinds**: what bytes mean on a stream: `http`, `ws`, `tcp`, or your
   own (§4).
4. **E2E**: a Noise handshake that turns one WebSocket (relayed or direct)
   into a private message channel, over which a second, inner mux session
   runs (§5).

Because (4) runs the same mux as (2), everything a client can do in plaintext
it can also do inside the encrypted session, including opening `http`, `ws`,
`tcp` and custom streams, and the agent can open streams back to the client.

## 1. Codes, tokens and connection strings

### 1.1 Derivation

```
code          = 32 random bytes                        (CSPRNG, generated by the agent)
prk           = HKDF-Extract(salt = "bolthole/v1", ikm = code)           # SHA-256
routing_token = base64url_nopad(HKDF-Expand(prk, "routing-token", 24))   # 32 chars
psk           = HKDF-Expand(prk, "e2e-psk", 32)
token_hash    = lowercase_hex(SHA-256(ASCII(routing_token)))             # 64 chars
```

* The relay only ever sees `routing_token` (in client URLs) and `token_hash`
  (from agents). Neither reveals `code` or `psk`.
* A **public** agent (plaintext mode, §6) may instead pick any random
  `routing_token` matching `[A-Za-z0-9_-]{16,128}` and publish it.

### 1.2 Connection string

A connection string is a normal URL with the code in the fragment, which
browsers and HTTP libraries never send to a server:

```
https://relay.example.com/#k=<base64url_nopad(code)>
http://127.0.0.1:8787/base/path/#k=<…>          # dev, or a relay mounted under a prefix
```

Clients derive `routing_token` from the code and talk to
`<relay base>/c/<routing_token>/…`. Other fragment parameters (`&name=…`) are
allowed and must be ignored if unknown.

## 2. Relay endpoints

| Endpoint | Purpose |
| --- | --- |
| `GET /healthz` | `{"ok":true,"version":"…","edition":"…"}` |
| `GET /v1/agent?th=<token_hash>` (WebSocket) | Agents register here (§2.1). `th` lets path-routed relays (Cloudflare) pick the right shard before the hello arrives. |
| `ANY /c/<routing_token>/<rest>` | Tunneled HTTP. Becomes an `http` stream to the agent with `path = "/" + rest` (query included). |
| `GET /c/<routing_token>/<rest>` (WebSocket) | Tunneled WebSocket. Becomes a `ws` stream. `/c/<token>/.bolthole/e2e` is the E2E entry point (§5). |

Relays respond `502` with `{"error":"agent_offline"}` when no agent holds the
token, and map stream resets (§3.5) to status codes:

| reset code | HTTP |
| --- | --- |
| `not_found` | 404 |
| `forbidden`, `e2e_required` | 403 |
| `refused`, `overloaded`, `going_away` | 503 |
| `timeout` | 504 |
| anything else | 502 |

### 2.1 Agent registration

The agent dials `wss://<relay>/v1/agent?th=<token_hash>` (WebSocket
subprotocol `relay.v1`). The first message
in each direction is a **text** JSON object; everything after is binary mux
frames (§3).

```jsonc
// agent → relay
{"type":"hello","v":1,"token_hash":"<64 hex>","name":"my-laptop","auth":"<optional key or JWT>",
 "caps":["mux/1"]}

// relay → agent, success
{"type":"welcome","v":1,"heartbeat_ms":20000,"max_streams":256,"max_frame":1048581}

// relay → agent, failure (then the socket is closed with the matching close code)
{"type":"error","code":"unauthorized","message":"bad key"}
```

| Close code | Meaning | Agent should |
| --- | --- | --- |
| `4000` | Another agent registered the same `token_hash` and replaced this one. | Back off to the maximum delay before redialing, so two agents sharing a code don't flap. |
| `4001` | Protocol error (bad hello, bad frame). | Fix the bug; redial with backoff. |
| `4002` | Invalid `token_hash`. | Stop. |
| `4003` | Unauthorized. | Stop and surface the error. |
| `4004` | Rate limited. | Redial with backoff. |
| `1001` / `1012` | Relay restarting or going away. | Redial with backoff. |

Unknown fields in either message must be ignored; that is how the protocol
grows (`caps` advertises optional features).

### 2.2 Authentication

Relays decide whether an agent may register. The reference relay ships three
policies and an interface for more:

* **open**: anyone may register (still cannot reach anyone else's agent without their code);
* **shared key**: `auth` must equal a configured key (compared in constant time);
* **JWT**: `auth` is an HS256 JWT with `aud: "bolthole"`, `sub`, `exp`.

Relays also rate-limit registrations and client connections per IP, and
hold a client request for a few seconds (default 5 s) when its agent is
momentarily offline, so an agent reconnect is invisible to clients.

## 3. Mux

### 3.1 Frames

Every frame is one binary transport message:

```
 0        1                    5
+--------+--------------------+------------------------+
|  type  |  stream_id (u32 BE) |  payload (0..N bytes)  |
+--------+--------------------+------------------------+
```

| type | name | stream | payload |
| --- | --- | --- | --- |
| `0x01` | `OPEN` | new id | UTF-8 JSON `{"kind":"…","meta":{…}}` |
| `0x02` | `ACCEPT` | id | UTF-8 JSON meta object (may be `{}` or empty) |
| `0x03` | `DATA` | id | bytes |
| `0x04` | `FIN` | id | empty. Sender will send no more `DATA` on this stream (half close). |
| `0x05` | `RESET` | id | UTF-8 JSON `{"code":"…","message":"…"}`. Aborts the stream both ways. |
| `0x06` | `WINDOW` | id, or 0 | u32 BE: additional bytes the peer may send on this stream, or on the whole session for id 0. |
| `0x07` | `PING` | 0 | 0–64 opaque bytes. |
| `0x08` | `PONG` | 0 | the `PING` payload, echoed. |
| `0x09` | `GOAWAY` | 0 | UTF-8 JSON `{"code":"…","message":"…"}`. No new streams; existing ones may finish. |

* Receivers **must ignore** frame types they don't know. New frame types are
  added this way without a version bump.
* Maximum frame size is `max_frame` bytes (default **1 MiB + 5**). A larger
  frame is a protocol error.
* Frames for an unknown or already-closed stream are dropped, except `OPEN`.
  A receiver may answer them with `RESET {"code":"unknown_stream"}`.

### 3.2 Stream ids

The side that **dialed** the transport opens streams with odd ids (1, 3, 5…);
the side that **accepted** it uses even ids (2, 4, 6…). Ids are never reused
within a session. On the agent socket the relay accepted the WebSocket, so
relay-initiated streams are even. In an E2E session the client dialed, so
client streams are odd and agent-initiated streams are even.

### 3.3 Lifecycle

```
opener                                  acceptor
OPEN {kind, meta}  ───────────────────▶
DATA… (allowed immediately, within the initial window)
                   ◀───────────────────  ACCEPT {meta}     or  RESET {code}
DATA / FIN         ◀──────────────────▶  DATA / FIN
```

* A stream is finished when both sides have sent `FIN`, or either side has
  sent `RESET`.
* Opening more than `max_streams` concurrent streams is answered with
  `RESET {"code":"refused"}`.
* An acceptor with no handler for `kind` answers `RESET {"code":"unsupported_kind"}`.

### 3.4 Flow control

Each direction of each stream starts with a window of **4194304 bytes** (4 MiB). Only
`DATA` payload bytes count. A sender must not send more than the current
window; a receiver that sees an overrun resets the stream with
`flow_control`. After the application consumes bytes, the receiver returns
credit with `WINDOW`. The reference implementations return credit once half
the window has been consumed. Senders should split `DATA` into chunks of at
most 32 KiB so one busy stream doesn't hold the transport for long.

Each direction of the session as a whole also starts with a window of
**67108864 bytes** (64 MiB), shared by all its streams, so a peer can't make
the receiver buffer `max_streams × 4 MiB`. A `DATA` payload counts against
both its stream's window and the session window; a sender sends only what
both allow. A receiver that sees the session window overrun closes the
session. The receiver frees bytes when the application consumes them, and
also when it discards them (`DATA` for an unknown, reset or finished stream,
and data still buffered when a stream is reset), and returns session credit
with `WINDOW` on stream 0, once half the session window is free.

### 3.5 Reset codes

`cancel`, `refused`, `unsupported_kind`, `not_found`, `forbidden`,
`e2e_required`, `timeout`, `flow_control`, `protocol_error`, `internal`,
`going_away`, `unknown_stream`. Implementations may add their own; unknown
codes are treated as `internal`.

### 3.6 Liveness

Each side sends `PING` every `heartbeat_ms` (default 20 s) when it has sent
nothing else for that long, and answers every `PING` with a `PONG`. A side
that has received nothing at all for `3 × heartbeat_ms` closes the session.

### 3.7 GOAWAY and draining

A relay that is shutting down sends `GOAWAY {"code":"going_away"}` on every
agent socket. Agents immediately dial a fresh connection (make-before-break)
and let streams on the old one finish. A relay keeps routing new requests to
the most recently registered session for a `token_hash`.

## 4. Stream kinds

The `kind` string decides how a stream's bytes are interpreted. Names without
a dot are reserved for this spec; anything else (`com.example.rpc`,
`myapp.sync`) is yours. Names starting with `relay.` are reserved for relay
services.

### 4.1 `http`

```jsonc
// OPEN meta
{"method":"POST","path":"/api/items?x=1","headers":{"content-type":["application/json"]}}
// ACCEPT meta
{"status":200,"headers":{"content-type":["text/event-stream"]}}
```

The opener sends the request body as `DATA` and then `FIN` (immediately if
there is no body). The acceptor sends `ACCEPT`, the response body as `DATA`,
then `FIN`. Bodies stream in both directions, so Server-Sent Events, chunked
uploads and long polls work. Header names are lowercase; values are arrays.
Hop-by-hop headers (`connection`, `keep-alive`, `transfer-encoding`,
`upgrade`, `te`, `trailer`, `proxy-*`) are not forwarded.

### 4.2 `ws`

```jsonc
// OPEN meta
{"path":"/live","headers":{…},"protocols":["chat.v2"]}
// ACCEPT meta
{"protocol":"chat.v2"}
```

Both directions carry WebSocket messages as **records**:

```
+--------+-----------------+-----------------+
| op u8  | length (u32 BE) | payload         |
+--------+-----------------+-----------------+
op: 0x01 text, 0x02 binary, 0x08 close (payload = u16 BE code + UTF-8 reason)
```

Records may be split across `DATA` frames and several records may share one.
After a close record the sender sends `FIN`. Maximum record payload is 16 MiB.

### 4.3 `tcp`

```jsonc
// OPEN meta
{"target":"ssh"}     // a name the agent maps to an address; "" = the agent's default
```

Raw bytes both ways. Agents must only connect to targets they were
explicitly configured with.

## 5. End-to-end encryption

### 5.1 Entry points

The handshake runs over any WebSocket whose binary messages are delivered in
order:

* **Relayed**: the client opens `wss://<relay>/c/<routing_token>/.bolthole/e2e`.
  The relay forwards it like any other WebSocket (a `ws` stream with
  `path = "/.bolthole/e2e"`); the agent recognises the reserved path.
* **Direct**: an agent may also listen locally (LAN, VPN, Tailscale) and
  serve `GET /.bolthole/e2e` itself. The handshake is identical, so a direct
  path is exactly as authenticated as a relayed one.

### 5.2 Handshake

`Noise_NNpsk0_25519_AESGCM_SHA256` ([Noise spec](https://noiseprotocol.org/noise.html)
rev 34), prologue `"bolthole/v1"`, PSK = `psk` from §1:

```
-> psk, e        msg1 = e_c (32) ‖ AEAD(ClientHello JSON)
<- e, ee         msg2 = e_a (32) ‖ AEAD(AgentHello JSON)
```

Each message is one binary WebSocket message.

```jsonc
// ClientHello (encrypted in msg1)
{"protos":["mux/1"],"name":"alice's phone","extra":{}}
// AgentHello (encrypted in msg2)
{"proto":"mux/1","name":"my-laptop","direct":["ws://192.168.1.20:7777/.bolthole/e2e"],"extra":{}}
```

* Only a holder of the code can produce msg1 (its payload is encrypted under
  a PSK-derived key) or msg2, so the relay can neither read nor
  man-in-the-middle the session. The client is authenticated implicitly: the
  agent must not act on anything before the first transport record
  decrypts. Ephemeral keys give forward secrecy.
* `protos` is an ordered list of application protocols (like TLS ALPN). The
  agent picks one; the client aborts if it isn't one it offered. `mux/1` runs
  the inner mux session below. Applications may define their own names and
  use the raw channel instead.
* `direct` lists URLs where the agent can be reached without the relay. They
  travel inside the encrypted hello and never reach the relay in plaintext.
* Unknown hello fields are ignored. A refused or failed handshake simply
  closes the socket; no reason is sent.

### 5.3 Transport

After msg2 each direction uses its Noise `CipherState`: every WebSocket
message is one record, `AES-256-GCM(k, nonce = 0x00000000 ‖ u64 BE n, ad = "", plaintext)`,
with `n` counting from 0 per direction. Records carry at most 65 519
plaintext bytes (Noise's 65 535 minus the tag), so the inner session uses
`max_frame = 65519`. Any record that fails to decrypt (tampered, replayed,
dropped or reordered) closes the channel.

With `mux/1`, each record's plaintext is one mux frame (§3) of an **inner**
session in which the client is the dialer (odd stream ids) and the agent may
open streams back to the client (even ids).

### 5.4 Choosing a path

Clients race candidates: direct URLs first (from the connection string,
configuration, or a previous AgentHello), the relay after a short head start
(default 250 ms). The first completed handshake wins. A client on the relay
periodically retries direct candidates and moves new streams to a direct
session when one answers, then sends `GOAWAY` on the old session and closes
it once its streams finish. Clients may pin a path (relay only / direct only).

## 6. Modes

An agent runs in one of two modes:

* **E2E (default)**: the agent accepts only the `ws` stream to `/.bolthole/e2e`
  from the relay and resets everything else with `e2e_required`. The relay
  can at most see sizes and timing.
* **Public**: the agent also serves plaintext `http`/`ws` streams opened by the
  relay. Use it for things meant to be public, such as webhooks or a demo
  site, and publish `https://relay/c/<routing_token>/`.

---

## 7. Conformance checklist

An implementation is conformant when it:

- [ ] derives `routing_token`, `psk` and `token_hash` exactly as the test vectors say;
- [ ] encodes and decodes every frame in the test vectors, and ignores an unknown frame type;
- [ ] never sends beyond a peer's stream or session window, resets a stream that overruns its own window, and closes a session that overruns the session window;
- [ ] answers `PING` and closes a session silent for `3 × heartbeat_ms`;
- [ ] reproduces `msg1`, `msg2` and the first records in the test vectors byte for byte (given the fixed ephemeral keys);
- [ ] closes the session on the first record that fails to decrypt.
